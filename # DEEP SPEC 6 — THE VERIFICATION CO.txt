## 0. THE COOKBOOK PHILOSOPHY

Every artifact COCO produces must survive an escalating gauntlet of checks before a human sees it. The Verification Fabric is not a QA afterthought — **it is a first-class fabric with equal standing to Intelligence and Execution**.

### The Ten Governing Laws of Verification

```text
LAW 1  — GENERATION AND VERIFICATION ARE SEPARATE COGNITIVE PROCESSES
         The agent that produces work never grades its own work at L9.
         Independent critics are structural, not optional.

LAW 2  — VERIFICATION IS EXECUTED, NOT ASSERTED
         Every check is a running program with a machine-verifiable result.
         "I checked it" is not verification. A green test log is verification.

LAW 3  — EVERY LEVEL HAS EXPLICIT PASS CRITERIA
         "Looks good" is banned. Every check returns PASS | FAIL | SKIPPED
         | ERROR with structured evidence attached.

LAW 4  — FAILURE TRIGGERS DIAGNOSIS, NOT SILENCE
         Failed verification never returns a raw error to the user.
         It triggers root-cause analysis + repair + re-verification.

LAW 5  — VERIFICATION DEPTH MATCHES TASK RISK
         A one-liner code fix runs L0–L4. A production deployment
         runs L0–L10. Depth is chosen by policy, not by hope.

LAW 6  — EVERY CHECK PRODUCES REPRODUCIBLE EVIDENCE
         Logs, test output, screenshots, verification reports —
         attached as artifacts. Verification is auditable forever.

LAW 7  — VERIFICATION ITSELF IS VERIFIED
         The verifiers, critics, and test batteries are themselves
         benchmarked. A broken verifier is a system failure.

LAW 8  — HUMAN APPROVAL IS L10 — NOT AN AFTERTHOUGHT
         For destructive, high-stakes, or irreversible actions,
         a human approval gate is a first-class verification level.

LAW 9  — VERIFICATION IS BUDGETED
         Every check has a cost (compute, latency, license). Budgets
         are enforced. Excessive checks that don't improve outcomes
         are trimmed by the Evolution Fabric.

LAW 10 — REGRESSION IS FAILURE
         A previously-passing artifact that now fails triggers an
         incident. The system does not silently degrade.
```

### Design Principles

```text
1. LEVELS ARE SERIAL, CHECKS WITHIN A LEVEL ARE PARALLEL
   L1 must pass before L2 begins. Within L4 (unit tests), all suites run parallel.

2. EARLY EXIT ON HARD FAILURE
   A hard-fail (e.g., artifact does not exist at L0) short-circuits.
   No point running unit tests on a file that failed to write.

3. CONTINUE ON SOFT FAILURE
   A soft-fail (e.g., style violation at L3) logs but continues.
   Repair may fold multiple soft-fails into a single fix pass.

4. EVERY CHECK RUNS IN A DEDICATED SANDBOX
   Runners share nothing. A misbehaving check cannot poison another.

5. RESULTS ARE APPEND-ONLY
   Once a LevelResult is emitted, it's immutable. Re-runs create new rows.
```

## 3. THE VERIFICATION PLANNER

The planner selects **which levels to run for which task**. It converts a `VerificationRequest` (Deep Spec 2 §7.1) into an ordered execution plan.

### 3.1 Level Selection Policy

```python
def select_levels(
    task: Task,
    mission: Mission,
    domain: VerificationDomain,
    tier: MissionTier,
    autonomy: AutonomyLevel,
    verification_level: int,   # target_level from task spec
) -> list[int]:
    """
    Levels 0..target_level are always attempted; additional gates
    may be added based on risk and tier.
    """
    levels = list(range(0, verification_level + 1))

    # Rule 1: L9 (critic) is mandatory for Tier 3+ specialists at Rung 3+
    if _uses_rung3plus_specialist(task) and 9 not in levels:
        levels.append(9)

    # Rule 2: L10 (human) is mandatory for:
    #   - autonomy in {L4_CHECKPOINTED, L5_CONTINUOUS} on destructive actions
    #   - deployment tasks in production
    #   - any task explicitly flagged requires_human_approval
    if _requires_human_gate(task, mission, autonomy):
        levels.append(10)

    # Rule 3: Default tier caps L8-L10 to prevent budget exhaustion
    if tier == MissionTier.DEFAULT:
        levels = [l for l in levels if l <= 7 or _explicitly_requested(task, l)]

    # Rule 4: Enterprise adds L7 domain-specific compliance scans by default
    if tier == MissionTier.ENTERPRISE:
        if 7 not in levels: levels.append(7)

    return sorted(set(levels))
```

### 3.2 Verification Budget

Every verification carries a compute + latency budget derived from the mission's `ResourceBudget`.

```yaml
default_verification_budgets:
  default:
    max_seconds: 60
    max_compute_seconds: 120
    max_critic_calls: 1
  pro:
    max_seconds: 600
    max_compute_seconds: 1800
    max_critic_calls: 3
  ranger:
    max_seconds: 3600
    max_compute_seconds: 36000
    max_critic_calls: unlimited
  enterprise:
    per_contract: true
```

If budget is exhausted mid-run, remaining checks are marked `SKIPPED_BUDGET`; verdict computation accounts for skipped levels.

## 4. THE CHECK REGISTRY

Every concrete check is a first-class registry entry. This enables the Evolution Fabric to measure per-check accuracy, cost, and latency and evolve the batteries over time.

### 4.1 Check Descriptor Schema

```protobuf
message CheckDescriptor {
  string check_id                = 1;   // e.g. "software.l3.ruff"
  string check_name              = 2;
  int32  applies_to_level        = 3;   // 0..10
  repeated VerificationDomain applies_to_domains = 4;

  string tool_id                 = 5;   // Registry reference (Deep Spec 2 §4.3)
  google.protobuf.Struct default_params = 6;

  bool   soft                    = 7;   // Soft fail continues; hard fail blocks
  bool   idempotent              = 8;
  int32  timeout_ms              = 9;
  int32  typical_cost_millis     = 10;

  string pass_criterion          = 11;  // Human-readable spec
  string evidence_kind           = 12;  // "log", "json_report", "screenshot"

  // Observed performance (populated by Evolution Fabric)
  double false_positive_rate     = 13;
  double false_negative_rate     = 14;
  double median_latency_ms       = 15;
}
```

### 4.2 Check Runner Contract

Every check is an implementation of the `CheckRunner` interface — sandboxed, deadline-aware, and metric-emitting.

```python
class CheckRunner(ABC):
    check_id: str
    tool_id: str

    @abstractmethod
    async def run(
        self,
        artifacts: list[ArtifactRef],
        params: dict,
        sandbox: SandboxHandle,
        deadline_ms: int,
    ) -> CheckResult:
        """
        MUST:
          - Execute within deadline
          - Emit CheckResult with status, message, details, evidence_ref
          - Attach reproducible evidence (log artifact, structured report)
          - Never mutate artifacts (verification is read-only)
        """
```

## 6. CRITIC PROMPT LIBRARY (L9 CANONICAL PATTERNS)

Every domain critic runs a **structured attack pattern**. The following are the canonical prompt scaffolds (values in `{{}}` are filled by the runtime).

### 6.1 Universal Critic Header

```text
You are the paired adversarial critic for {{specialist_id}}.
Your role is not to help. Your role is to find every reason this work
could be wrong, incomplete, or unsafe before it reaches the user.

Constitutional Standard:
- Every finding must cite specific evidence (line, quote, source).
- Vague criticism ("this could be better") is banned; be concrete.
- Rank findings: BLOCKER | MATERIAL | ADVISORY.
- Recommend: ACCEPT | ACCEPT_WITH_NOTES | REVISE | REJECT | ESCALATE.

Attack Patterns to Execute (in order):
{{attack_patterns_yaml}}

Deliverable Under Review:
{{artifacts_summary}}

Full Artifacts:
{{artifacts_ref_list}}

Domain Corpus Available:
{{corpus_summary}}
```

### 6.2 Attack Pattern Templates

Each domain critic gets patterns like:

```yaml
citation_verification:
  instruction: >
    For every citation in the deliverable, re-fetch the source and verify
    the quoted text appears verbatim. Any citation that fails resolution,
    fails quote-match, or has been overturned/superseded is a BLOCKER.

counter_argument_check:
  instruction: >
    For the deliverable's main conclusion, search the corpus for authorities
    holding the opposite. If any binding contrary authority exists that is
    not addressed or distinguished, flag as MATERIAL.

reasoning_soundness:
  instruction: >
    For each logical step, verify the conclusion follows from the premise.
    Any leap without support is a MATERIAL finding.

edge_case_probe:
  instruction: >
    Enumerate 5 edge cases the deliverable might fail on. Test each against
    the deliverable's logic/output. Any failure is MATERIAL.

adversarial_reformulation:
  instruction: >
    Assume a hostile counterparty will use this deliverable against your
    client / user. What is the strongest attack? Is it addressed?
```

### 6.3 Critic Output Contract

Critics return a **CriticReport** (per Deep Spec 2 §7.2) with structured scores and recommendation. The Verification Fabric enforces schema conformance.

```yaml
critic_report_required_fields:
  - correctness_score       # 0..1
  - completeness_score      # 0..1
  - consistency_score       # 0..1
  - evidence_quality_score  # 0..1

  - overall_score           # 0..1
  - strengths               # list
  - weaknesses              # list

rejection_rules:
```

## 7. THE REPAIR LOOP

When verification fails, the Repair Loop kicks in. It is a **first-class subsystem**, not an afterthought.

### 7.1 Loop Architecture

```text
             Verification failure
                     │
                     ▼
       ┌─────────────────────────┐
       │ 1. FAILURE CLASSIFIER   │
       │    → ErrorCategory       │
       │    → severity            │
       └─────────────┬────────────┘
                     ▼
       ┌─────────────────────────┐
       │ 2. ROOT-CAUSE ANALYZER  │
       │    - trace failure to    │
       │      artifact + step     │
       │    - identify probable   │
       │      cause               │
       └─────────────┬────────────┘
                     ▼
       ┌─────────────────────────┐
       │ 3. STRATEGY SELECTOR    │
       │    - pick repair        │
       │      strategy from      │
       │      catalog            │
       │    - or synthesize new  │
       └─────────────┬────────────┘
                     ▼
       ┌─────────────────────────┐
       │ 4. REPAIR ASSIGNMENT    │
       │    - assign to           │
       │      original agent OR   │
       │      specialized fixer   │
       └─────────────┬────────────┘
                     ▼
       ┌─────────────────────────┐
       │ 5. REPAIR EXECUTION     │
       │    - agent runs repair  │
       │    - produces new       │
       │      artifact version   │
       └─────────────┬────────────┘
                     ▼
       ┌─────────────────────────┐
       │ 6. RE-VERIFICATION      │
       │    - full battery re-run│
       │    - focused on failed   │
       │      levels + regressions│
       └─────────────┬────────────┘
                     ▼
              ┌──────┴──────┐
              │             │
            PASS          FAIL
              │             │
              │       attempt_number++
              │             │
              │        max_attempts?
              │             │
              │       ┌─────┴─────┐
              │       NO         YES
              │       │           │
              │    back to 1   ESCALATE
              │                    │
              ▼                    ▼
           DONE                HUMAN GATE
                                or ABANDON
```

### 7.2 Failure Classifier

Uses the `ErrorCategory` enum from Deep Spec 2 §4.2 plus verification-specific extensions:

```python
class FailureClassifier:
    def classify(self, check_result: CheckResult, artifact: ArtifactRef) -> Classification:
        # Deterministic rules first (fast, cheap)
        if check_result.check_id.endswith(".mypy_strict"):
            return Classification(
                category=ErrorCategory.LOGIC,
                subcategory="type_error",
                confidence=0.95,
                strategy_hint="fix_type_annotations",
            )
        if check_result.check_id.endswith(".balance_identity"):
            return Classification(
                category=ErrorCategory.LOGIC,
                subcategory="balance_sheet_plug",
                confidence=0.99,
                strategy_hint="rebuild_bs_linkage",
            )
        if check_result.check_id.endswith(".every_citation_resolves"):
            return Classification(
                category=ErrorCategory.REQUIREMENT,
                subcategory="fabricated_citation",
                confidence=0.99,
                strategy_hint="regenerate_with_verified_sources",
            )
        # ... many rules ...

        # Fall back to LLM classifier for novel failures
        return self._llm_classify(check_result, artifact)
```

### 7.3 Repair Strategy Catalog

```yaml
strategies:

  fix_type_annotations:
    applies_to: [software.l2.python.mypy_strict, software.l2.typescript.tsc_strict]
    approach: >
      Attach mypy/tsc output as context to the specialist. Instruct: fix each
      type error individually, then re-run typecheck locally before returning.
    max_iterations: 3

  rebuild_bs_linkage:
    applies_to: [finance.l5.balance_identity]
    approach: >
      Attach balance sheet + cash flow + IS to C48. Instruct: trace retained
      earnings roll-forward, verify working capital linkages, verify PP&E
      + AD roll-forward, verify debt roll-forward. Do NOT plug.
    max_iterations: 2

  regenerate_with_verified_sources:
    applies_to: [research.l4.*, legal.l4.every_citation_resolves]
    approach: >
      Discard fabricated citations. Instruct specialist to re-search corpus,
      cite only sources returned by tool calls with valid content hashes.
    max_iterations: 2

  patch_missing_test:
    applies_to: [software.l6.requirement_traceability]
    approach: >
      For each requirement without a test, generate the missing test.
      Prefer property-based tests where applicable.
    max_iterations: 2

  refactor_complexity:
    applies_to: [software.l8.cyclomatic_complexity]
    approach: >
      For each function exceeding threshold, extract sub-functions to reduce
      cyclomatic complexity below 10.
    max_iterations: 2

  address_critic_findings:
    applies_to: [level_9_critic]
    approach: >
      For each critic finding: read the specific evidence, apply the specific
      fix suggested (if any), then re-run only the failed attack pattern.
    max_iterations: 3

  security_finding_fix:
    applies_to: [software.l7.*]
    approach: >
      For each high/critical finding: identify the exact code location, apply
      the well-known remediation, then re-scan.
    max_iterations: 2

  playbook_gap_close:
    applies_to: [legal.l6.playbook_coverage]
    approach: >
      For each unaddressed BLOCKER or MATERIAL playbook item: analyze the
      clause, propose specific redline, integrate into deliverable.
    max_iterations: 2
```

### 7.4 Repair Escalation

```text
Escalation triggers:

  1. max_attempts reached without pass
     → RepairOrder.status = ABANDONED
     → task.status = FAILED
     → mission enters BLOCKED phase pending user input

  2. same-category failure across all attempts
     → same root cause not being addressed
     → escalate to Tier 2 Domain Director
     → Director may: assign different specialist, revise scope, request user clarification

  3. failure category CRITICAL security or safety
     → escalate immediately to A6 Risk Officer
     → no retry without human approval

  4. verification budget exhausted mid-loop
     → partial repair recorded
     → user notified: "N of M checks passing; want to continue or accept?"
```

## 9. VERIFICATION BUDGETING

Per Law 9, verification is budgeted. The Verification Fabric enforces envelopes without silently degrading quality.

### 9.1 Budget Enforcement

```python
class VerificationBudgetEnforcer:
    async def check_can_run(
        self,
        planned_checks: list[CheckDescriptor],
        remaining_budget: VerificationBudget,
    ) -> BudgetDecision:
        estimated_cost = sum(c.typical_cost_millis for c in planned_checks)
        estimated_time = self._critical_path_ms(planned_checks)

        if estimated_time > remaining_budget.max_wall_ms:
            return BudgetDecision(
                fits=False,
                overflow_ms=estimated_time - remaining_budget.max_wall_ms,
                recommendation="skip_soft_checks_or_extend_budget",
            )
        return BudgetDecision(fits=True)
```

### 9.2 Skipping Policy

When budget forces skips:

```text
1. NEVER skip hard checks
2. NEVER skip L7 (security) checks
3. NEVER skip L9 (critic) for Rung 3+ specialists
4. Prefer skipping L8 soft performance checks first
5. Prefer skipping L3 style checks second
6. Log every skip with reason=BUDGET_EXHAUSTED
7. User-facing message notes the skip
```

### 9.3 Budget Amendment Flow

If a mission needs more verification than budgeted:

```text
1. Verification Planner emits `mission.verification_budget_warning`
2. If auto-scaling authorized (Pro/Ranger): budget auto-extended once
3. If auto-scaling denied: user prompted "extend budget?" with cost estimate
4. Extension recorded as decision
```

```sql
CREATE MATERIALIZED VIEW verification.v_check_performance AS
SELECT
  check_id,
  date_trunc('day', started_at) AS day,
  COUNT(*)                       AS runs,
  AVG(CASE WHEN status = 'passed' THEN 1 ELSE 0 END) AS pass_rate,
  AVG(duration_ms)               AS avg_duration_ms,
  PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY duration_ms) AS p95_duration_ms
FROM verification.check_results cr
JOIN verification.level_results lr USING (level_result_id)
JOIN verification.verifications v USING (verification_id)
GROUP BY check_id, date_trunc('day', started_at);
```

## 12. THE VERIFICATION SDK

To make it trivial for domain teams to add new checks and critics, COCO exposes a small internal SDK.

### 12.1 Registering a New Check

```python
from coco.verification import check, ArtifactRef, CheckResult

@check(
    check_id="finance.l5.working_capital_rollforward",
    applies_to_level=5,
    applies_to_domains=["FINANCIAL"],
    tool_id="wc_rollforward_verifier",
    soft=False,
    idempotent=True,
    timeout_ms=15000,
    pass_criterion="AR + Inventory - AP roll-forward reconciles to CFS Δ WC",
)
async def working_capital_rollforward(
    artifacts: list[ArtifactRef],
    params: dict,
    sandbox: SandboxHandle,
    deadline_ms: int,
) -> CheckResult:
    xlsx = await sandbox.load_artifact(artifacts[0])
    model = FinancialModel.load(xlsx)

    for period in model.forecast_periods():
        delta_ar = model.ar[period] - model.ar[period - 1]
        delta_inv = model.inventory[period] - model.inventory[period - 1]
        delta_ap = model.ap[period] - model.ap[period - 1]
        cfs_wc_change = model.cf_statement[period].working_capital_change

        expected = -(delta_ar + delta_inv - delta_ap)
        if abs(expected - cfs_wc_change) > 0.005:
            return CheckResult.failed(
                message=f"Working capital roll-forward mismatch in {period}",
                details={
                    "expected": expected,
                    "actual": cfs_wc_change,
                    "delta": cfs_wc_change - expected,
                },
                evidence_artifact_ref=await sandbox.write_evidence(
                    "wc_rollforward_diff.json", details
                ),
            )
    return CheckResult.passed(message="WC roll-forward reconciles across all periods")
```
